## 1장 Designing Systems

### 핵심 논지

웹과 앱을 “페이지 묶음”으로 보면 범위·공수·품질을 잘못 판단하기 쉽다. 한 페이지는 단순한 한 덩어리가 아니며, 많은 페이지도 몇 개의 콘텐츠 유형과 레이아웃으로 구성될 수 있다. 따라서 프로젝트는 페이지 수보다 기능, 반복 패턴, 콘텐츠 구조, 통합 지점으로 산정해야 한다.

다양한 화면 크기, 장치, 브라우저, 입력 방식, 환경을 감당하려면 거대한 화면을 작은 책임 단위로 분해하는 모듈성이 필요하다. 이 모듈성은 코드에만 적용되는 기술이 아니라 전략, 프로세스, 콘텐츠, 시각 디자인, UI 설계를 함께 바꾸는 원칙이다.

### 영역별 의미

#### 전략

- 몇 년마다 전면 교체하는 대형 리디자인은 사용자가 익힌 인터페이스를 흔들고, 조직의 잘못된 운영 방식을 그대로 반복시킨다.
- 더 작은 단위로 출시하고 사용자 피드백을 반영하는 지속적 개선이 시스템적 접근과 맞는다.
- 큰 리디자인이 필요해도 구조적 부품과 학습을 모두 버리는 방식은 피한다.

#### 프로세스

- 특정 Agile 프레임워크를 이름만 도입하는 것보다 변화 수용, 작은 단위, 빠른 실제 환경 검증, 다학제 협업이 중요하다.
- 조직의 제약과 사람에 맞는 프로세스를 설계하되, 긴 인수인계 사슬은 줄인다.

#### 콘텐츠

- 콘텐츠는 한 페이지에 고정된 덩어리가 아니라 여러 채널과 장치에서 재조합될 수 있는 구조화된 청크로 다룬다.
- CMS와 데이터 모델은 “한 번 만들고 다양한 맥락에서 발행”할 수 있도록 의미 단위와 필드를 보존해야 한다.

#### 코드

- 관심사 분리, 단일 책임, 객체·모듈 사고가 JavaScript뿐 아니라 CSS와 마크업 구조에도 필요하다.
- 재사용은 중복 코드를 줄이는 목적을 넘어 동일한 행동과 품질을 여러 화면에 확산하는 수단이다.

#### 시각 디자인

- 모든 페이지의 완성 시안을 먼저 만드는 방식은 다양한 화면과 실제 동작을 충분히 표현하지 못한다.
- 색, 타이포그래피, 질감, 이미지 방향 같은 “디자인 분위기”는 스타일 타일과 요소 콜라주처럼 레이아웃 확정을 늦추는 산출물로 먼저 탐색할 수 있다.
- 이 산출물은 예쁜 그림에 대한 취향 반응보다 목표와 시각 방향에 대한 대화를 유도한다.

#### 시스템 UI

- 반응형 디자인은 페이지를 줄였다 늘리는 문제가 아니다. 내비게이션, 모달, 목록, 입력, 미디어 등 각 패턴이 다양한 컨테이너와 입력 환경에서 어떻게 행동하는지 설계해야 한다.
- 범용 UI 프레임워크는 빠른 시작, 검증된 패턴, 일관성을 주지만 브랜드 동질화, 불필요한 코드, 구조와 이름의 충돌, 과도한 커스터마이징 비용을 만들 수 있다.
- 결론은 모든 프로젝트에 동일한 프레임워크를 쓰는 것이 아니라, 프로젝트와 조직에 맞는 작은 시스템을 만드는 것이다.

### 스타일 가이드 생태계

원문은 디자인 시스템을 UI 컴포넌트 목록만으로 보지 않는다. 서로 연결된 지침이 필요하다.

- 브랜드 정체성: 로고, 색, 타이포그래피, 핵심 메시지와 브랜드 자산.
- 디자인 언어: 제품군을 관통하는 철학, 방향, 시각·행동 원칙.
- 보이스와 톤: 일관된 목소리와 상황에 따라 달라지는 정서적 강도.
- 글쓰기: 문법, 표기, 콘텐츠 기여 규칙.
- 코드: 읽기 쉽고 유지 가능한 구현 규칙과 예시.
- 패턴 라이브러리: 실제 UI 패턴, 사용법, 상태, 코드와 맥락.

### 기대 효과

- 일관성은 사용자의 재학습 부담을 줄이고 신뢰를 높인다.
- 공통 이름은 디자이너, 개발자, 콘텐츠, 비즈니스, 외부 파트너 사이의 오해를 줄인다.
- 패턴을 보여주는 문서는 이해관계자에게 화면 뒤의 시스템을 교육한다.
- 한 패턴에 여러 직군의 제약과 모범 사례를 모으면 서로의 판단을 이해하기 쉬워진다.
- 격리된 컴포넌트 검증은 브라우저 오류, 성능, 접근성 문제의 원인을 좁힌다.
- 초기 비용 이후 재사용이 늘면서 새 기능과 화면의 제작 속도가 빨라진다.
- 분석, 사용자 테스트, 실험, 운영 경험을 시스템에 환류하면 시간이 갈수록 가치가 커진다.

### 실패 위험

- 단기 예산과 일정만 보면 초기 시스템 투자가 밀린다.
- 패턴 라이브러리를 본 제품과 별도인 부가 프로젝트로 취급하면 가장 먼저 중단된다.
- 소유자, 유지보수, 승인, 배포 계획이 없으면 문서와 실제 제품이 갈라진다.
- 개발자만 보는 기술 문서나 디자이너만 보는 갤러리가 되면 공통 언어 기능을 잃는다.
- 각 패턴이 언제, 어디에서 쓰이는지 없으면 변경 영향과 QA 범위를 알 수 없다.
- 이름과 분류 원칙 없는 컴포넌트 모음은 중복을 줄이지 못한다.

### 앞으로의 적용 규칙

- “몇 페이지인가?”보다 “어떤 사용자 행동, 콘텐츠 유형, 패턴, 상태, 외부 연동이 있는가?”로 범위를 정의한다.
- UI 변경을 화면 한 곳의 장식이 아니라 재사용 패턴과 소비 화면의 변화로 해석한다.
- 접근성, 성능, 반응형, 콘텐츠 구조를 선택적 추가 항목이 아니라 패턴의 기본 속성으로 둔다.
- 디자인 시스템 구축 자체를 최종 목적화하지 않는다. 사용자와 팀이 더 나은 제품을 더 안정적으로 만드는 수단이어야 한다.

## 2장 Atomic Design Methodology

### 다섯 계층

#### 1. Atoms

- 더 분해하면 기능적 의미를 잃는 기본 UI 요소다. 원문 예시는 레이블, 입력, 버튼, 이미지, 제목 같은 기본 요소다.
- 각 요소에는 크기, 타이포그래피, 색, 상태, 의미 같은 고유 속성이 있고, 이것이 상위 구성에서의 사용법을 결정한다.
- 격리된 예시는 기본 스타일을 한눈에 점검하는 데 좋지만, 실제 가치는 조합과 맥락에서 검증해야 한다.

#### 2. Molecules

- 소수의 atom이 한 가지 책임을 수행하도록 결합된 단순한 기능 단위다.
- 레이블+입력+버튼으로 이루어진 검색 폼처럼, 결합을 통해 각 요소의 목적과 상호작용이 명확해진다.
- 단일 책임을 지키면 테스트, 재사용, 일관성이 좋아진다. 기능을 계속 얹어 이해하기 어려운 만능 컴포넌트로 만들지 않는다.

#### 3. Organisms

- atom, molecule, 다른 organism이 모여 인터페이스의 독립적인 구역을 형성한다.
- 헤더처럼 서로 다른 부품을 묶을 수도 있고, 상품 그리드처럼 같은 molecule을 반복할 수도 있다.
- 작은 부품이 실제 맥락에서 어떻게 작동하는지 드러내며, 여러 템플릿에서 재사용할 수 있는 큰 패턴이 된다.

#### 4. Templates

- 컴포넌트를 레이아웃에 배치해 화면의 콘텐츠 구조와 위계를 표현하는 골격이다.
- 최종 문구보다 이미지 비율, 제목 길이, 반복 구조, 필수·선택 영역 같은 데이터 계약을 드러내야 한다.
- 여러 부품이 함께 작동하는지 확인하는 첫 전체 맥락이자, 다양한 실제 콘텐츠를 받아들이는 가드레일이다.

#### 5. Pages

- template에 대표성 있는 실제 콘텐츠를 넣은 구체적 시나리오다.
- 사용자가 만나는 최종 인터페이스이자, 하위 패턴이 현실을 견디는지 검증하는 테스트 무대다.
- 장바구니 1개/10개, 첫 사용자/재방문자, 짧은/매우 긴 제목, 일반/관리자 권한처럼 같은 template의 변이를 보여줘야 한다.
- 실패가 보이면 molecule, organism, template로 돌아가 시스템을 수정한다.

### 가장 중요한 해석: 비선형 사고모델

다섯 계층은 “atom을 모두 완성한 뒤 molecule을 만든다”는 순차 공정이 아니다. 세부 부품을 설계하면서 전체 화면을 보고, 실제 화면의 실패를 발견하면 다시 부품을 바꾸는 반복적 왕복이다.

- 부분은 전체의 요구를 받는다.
- 전체는 부분의 품질과 제약을 드러낸다.
- 추상적인 패턴 보기와 구체적인 페이지 보기를 계속 오간다.
- 격리 상태의 아름다움·기능성과 실제 화면 안의 아름다움·기능성을 둘 다 확인한다.

### 구조와 콘텐츠

- template은 콘텐츠 구조를, page는 대표 콘텐츠를 강조하지만 둘은 독립적으로 설계되지 않는다.
- 구조를 데이터에서 분리하면 재사용이 쉬워지지만, 콘텐츠 현실을 무시한 중립적 그릇을 만들면 깨진다.
- 실제 데이터가 줄바꿈, 비율, 밀도, 반복 수의 문제를 보이면 하위 패턴의 속성과 제약을 바꾼다.

### 이름과 분류

- atoms/molecules/organisms라는 말은 크기와 위계를 직관적으로 전달하기 위한 공통 언어다.
- 이 이름은 교리가 아니다. 팀이 더 잘 이해하는 Basics/Components/Features 같은 분류가 있다면 바꿔도 된다.
- 좋은 분류의 기준은 화학 비유를 지키는지가 아니라 협업자가 구조와 관계를 빠르게 이해하는지다.

### 적용 범위

- 방법론은 CSS나 JavaScript 아키텍처가 아니며 특정 웹 기술에 종속되지 않는다.
- 웹, 네이티브 앱, 데스크톱 소프트웨어, ATM 등 모든 인터페이스에 적용할 수 있다.
- 사용 흐름, 서비스 구조, 정보 아키텍처를 대신하지 않고 그것을 구현하는 UI 시스템을 조직한다.

### 현대적 보정: 디자인 토큰

원문은 오늘날의 디자인 토큰 체계를 중심 개념으로 다루지 않는다. 현대 프로젝트에서는 색, 간격, 타이포그래피, 반경, 그림자, 모션 같은 토큰을 atom의 고유 속성을 공급하는 foundation 또는 subatomic 구현층으로 둘 수 있다. 이는 원문의 “atom 자체” 정의와 동일하다고 단정하지 말고 프로젝트의 분류 규칙으로 명시한다.

## 3장 Tools of the Trade

### 핵심 논지

Pattern Lab은 Atomic Design을 실행하는 한 사례이며, 장의 본질은 특정 제품 추천이 아니라 좋은 패턴 라이브러리가 갖춰야 할 기능이다. 도구는 팀의 기술, 인프라, 작업 방식, 문화에 맞춰 선택한다.

### 패턴 라이브러리의 역할

- 실제 UI를 이루는 모든 패턴을 한곳에 모은다.
- 작은 패턴을 큰 패턴에 포함하고, 큰 패턴을 template에 배치해 중복 없는 조합 구조를 만든다.
- 하나의 하위 패턴 변경이 이를 소비하는 상위 구성에 반영되도록 한다.
- 최종 화면과 하부 시스템을 동시에 만들고, 버그를 특정 패턴까지 좁히며, 페이지 맥락에서 영향도 확인한다.

### 구조와 데이터를 분리하는 이유

- 기본 데이터와 페이지별 대표 데이터를 교체하면 같은 구조로 다양한 현실을 검증할 수 있다.
- placeholder만 보여주지 않고 긴 이름, 빠진 이미지, 관리자 권한, 반복 목록 등 동적 조건을 표현한다.
- 조건과 배열을 바꿔 변형을 만들면 중복된 정적 시안을 계속 만들 필요가 없다.
- 구조와 콘텐츠를 분리하면 콘텐츠 담당자가 안전하게 예시 데이터를 개선할 수 있고, 백엔드 개발자는 정적·동적 필드 계약을 이해하기 쉽다.

### 변형과 극단 조건

원문은 pseudo-pattern으로 기본 페이지 데이터를 상속한 뒤 특정 변수만 바꾸어 관리자 화면 등 변형을 만든다. 현대 도구에서는 story, fixture, test case, mock data, preview route 등으로 구현할 수 있다. 핵심은 “정상적인 한 화면”이 아니라 가능한 상태 공간을 적은 중복으로 표현하는 것이다.

### 좋은 패턴 라이브러리의 기능

1. **실제 대표 콘텐츠 주입:** 구조가 현실 데이터를 견디는지 확인한다.
2. **상태와 변형:** active/disabled뿐 아니라 역할, 데이터 양, 오류, 빈 상태 같은 시나리오를 표현한다.
3. **전체 해상도 스펙트럼:** 몇 개의 인기 기기 폭만이 아니라 사이 구간과 컨테이너 변화도 검사한다.
4. **관련 코드 보기:** 팀에 유용한 HTML, 템플릿, CSS, JavaScript 또는 컴포넌트 사용 API를 제공한다.
5. **살아 있는 설명과 주석:** 접근성, 성능, 콘텐츠, 디자인, 사용 제한을 실제 예시 옆에 둔다.
6. **lineage:** 무엇으로 구성됐는지와 어디에서 소비되는지를 양방향으로 보여준다.

### 단일 진실 공급원

- 이상적인 상태는 문서 예시와 실제 제품이 같은 컴포넌트 구현을 사용해 갈라지지 않는 것이다.
- 완전 동기화가 조직·기술상 과도하면, 적어도 코드 복사와 문서 수동 갱신의 마찰을 줄이고 버전·변경 범위를 명확히 한다.
- 코드가 보인다는 사실만으로 품질이 보장되지는 않는다. 리뷰, 테스트, 가이드, 소유권이 함께 있어야 한다.

### 도구 선택 질문

- 대표 콘텐츠와 상태 조합을 쉽게 만들 수 있는가?
- 다양한 viewport와 container에서 한 패턴을 검증할 수 있는가?
- 컴포넌트 API와 관련 코드를 팀이 재사용하기 좋은 방식으로 보여주는가?
- 설명, 제약, 접근성, 성능 주석을 예시 가까이에 둘 수 있는가?
- 하위 의존성과 상위 소비처를 찾을 수 있는가?
- 문서와 production implementation이 얼마나 자동으로 동기화되는가?

## 4장 The Atomic Workflow

### 사람과 설득

- 성공하는 시스템은 도구보다 실제 협업과 의사소통에 달려 있다.
- 디자인 시스템의 가치를 일관성 같은 전문 용어로만 설명하지 말고 시간, 비용, 출시 속도, 품질, 위험 감소, 전환과 같은 조직 성과에 연결한다.
- 구두 설득만으로 부족할 때는 현재 UI의 중복과 불일치를 한눈에 보여주는 interface inventory를 사용한다.

### Interface inventory 절차

1. **다학제 참여자 구성:** UX, 비주얼, 프론트·백엔드, 콘텐츠, PM, 비즈니스, QA 등 제품에 책임 있는 사람을 포함한다.
2. **공통 캡처 공간 선택:** 모두가 같은 형식으로 모을 수 있는 슬라이드나 보드 등을 선택한다.
3. **고유 패턴 캡처:** 같은 패턴의 모든 인스턴스가 아니라 서로 다른 각 패턴을 하나씩 모은다.
4. **분류:** 글로벌 요소, 내비게이션, 이미지, 아이콘, 폼, 버튼, 제목, 블록, 목록, 인터랙션, 미디어, 서드파티, 광고, 메시지, 색, 애니메이션 등을 제품에 맞게 조정한다.
5. **시간 제한:** 첫 패스는 대개 30~90분처럼 제한해 조사 자체가 목적이 되지 않게 한다.
6. **깊은 영역 포함:** 홈과 핵심 구매 흐름뿐 아니라 도움말, 404, 약관, 예외 화면 등 조직이 관리하는 모든 접점을 본다.
7. **발표와 이름 토론:** 분야별 결과를 공유해 동일 패턴의 서로 다른 이름과 이유를 드러낸다.
8. **통합과 후속 결정:** 빠진 항목을 보완하고 유지·삭제·통합할 패턴, 공통 이름, 살아 있는 라이브러리로 옮길 다음 단계를 정한다.

Inventory의 산출 효과는 네 가지다.

- 중복과 불일치를 시각적으로 드러낸다.
- 팀과 이해관계자의 공감대를 만든다.
- 패턴별 난이도와 제약으로 현실적인 범위·일정을 만든다.
- 공통 언어와 초기 패턴 집합을 제공한다.

### 디자인의 범위 재정의

디지털 디자인은 외관만이 아니다. 속도, 화면·컨테이너 크기, 네트워크, 장치 기능, 입력 방식, 사용 맥락, 사용성, 접근성, 선호, 인체공학이 함께 품질을 만든다.

따라서 시스템은 다음을 기본으로 포함한다.

- 다양한 능력과 보조기술을 포괄하는 접근성과 회복력.
- 특정 화면 폭에 고정되지 않는 유연한 레이아웃과 컴포넌트.
- 사용자의 시간과 데이터 비용을 존중하는 성능.
- 핵심 기능을 먼저 보장하고 환경 능력에 따라 강화하는 점진적 향상.
- 미래의 장치와 조건 변화를 받아들이는 구조.

### Waterfall 대신 병렬 협업

- UX 문서가 끝난 뒤 시각 시안, 그 뒤 개발로 넘기는 순차 인수인계는 중요한 제약을 너무 늦게 발견한다.
- UX, 비주얼, 프론트엔드의 활동량은 시기마다 달라도 프로젝트 내내 서로 자문한다.
- 프론트엔드 구현은 디자인을 복제하는 생산 단계가 아니라 반응형, 상호작용, 모션, 렌더링, 성능, 브라우저 현실을 결정하는 디자인 활동이다.
- 정적 산출물만 보여주면 이해관계자는 정적 그림만 승인하게 된다. 실제 환경의 프로토타입을 일찍 보여준다.

### 방향 설정

#### UX

- 고해상도 와이어프레임 전에 화면에 무엇이 어떤 순서로 필요한지 저해상도 구조로 합의한다.
- 작은 화면 제약을 활용하면 핵심 콘텐츠와 위계를 먼저 보게 된다.
- 콘텐츠 패턴과 표시 패턴을 구분하고, 간단한 목록이나 표로 목적·순서·재사용 가능성을 표현한다.

#### 비주얼

- 관련·비관련 업계의 다양한 화면을 짧게 보고 선호와 거부 이유를 말하게 해 미적 가치를 언어화한다.
- 스타일 타일로 색, 타이포그래피, 질감, 아이콘 방향을 탐색한다.
- 요소 콜라주로 그 분위기를 실제 UI 부품에 적용하되 전체 레이아웃 확정은 늦춘다.
- 큰 방향이 합의된 뒤에 전체 시안을 사용해 맥락을 보여주고, 이후 세부 반복은 실제 환경에서 진행한다.

#### 프론트엔드

- 첫날부터 저장소, 개발 환경, 기본 shell, 예상되는 로그인·검색·결제·헤더·푸터 등의 구조 마크업을 준비할 수 있다.
- 초기는 거칠어도 UX 가설과 기술 가능성을 함께 검증할 기반이 된다.
- 목적은 디자인 결정을 앞서 확정하는 것이 아니라 협업 가능한 실제 재료를 빠르게 만드는 것이다.

### 반복적 구축

- 한 패턴을 격리해 대화하면서 동시에 그 패턴을 사용하는 template/page도 본다.
- 완성도가 서로 다른 패턴이 섞인 중간 화면을 허용하되, 현재 상태와 다음 판단을 명확히 설명한다.
- 큰 공개 한 번보다 작은 rolling update와 짧은 피드백 루프를 선호한다.
- 정적 시안은 가설이다. 반응형, 동적 콘텐츠, 상호작용, 모션, 성능, 렌더링을 실제 환경에서 확인한 뒤 결정한다.
- 재사용 패턴이 성숙할수록 새 template은 기존 부품 조합으로 빨라진다.

### 원문의 권한 관련 조언을 적용할 때

원문은 접근성·성능·시스템 사고 같은 직업적 모범 사례를 기본 작업 방식에 포함하라고 강하게 주장한다. 이를 사용자 승인이나 조직 정책을 우회하라는 일반 권한으로 확대하지 않는다. 특히 전역 설정, 과금, 배포, 공개, 보안, 데이터 변경은 해당 환경의 승인 규칙을 우선한다.

## 5장 Maintaining Design Systems

### 산출물에서 제품으로

- 스타일 가이드 문서를 전달했다고 시스템이 살아남는 것은 아니다.
- 실제 제품과 문서가 갈라지는 순간 신뢰와 사용이 떨어지고, 화면별 hotfix가 시스템을 침식한다.
- 제품에서 발견한 문제를 한 화면만 고치기 전에, 같은 패턴이 쓰인 전체 생태계에서 개선해야 하는지 검토한다.
- 디자인 시스템은 완료일이 있는 부가 프로젝트가 아니라 roadmap, backlog, 예산, 사람, 지원을 가진 장기 제품이다.

### 1. Make it official

- 작은 pilot을 만든다.
- 실제로 시간·비용·품질에 도움이 된 증거를 보여준다.
- 그 뒤 소유자, 예산, 인력, roadmap, governance를 공식화한다.
- 큰 선투자를 설득하기 어렵다면 유용한 작은 시스템부터 가치를 증명한다.

### Maker와 user

- maker는 시스템을 만들고 유지·승인·배포·지원한다.
- user는 제품과 기능에서 패턴을 사용하고 요구·버그·맥락을 피드백한다.
- maker는 전체 생태계 관점을, user는 특정 제품의 현장 관점을 제공한다.
- 모든 사람이 직접 시스템을 편집할 필요는 없지만 누군가는 명시적으로 소유해야 한다.
- 핵심 제작자는 UX, 비주얼, 프론트엔드가 될 수 있고, 콘텐츠, 백엔드, PM, 경영, 실제 사용팀은 필요한 판단에 참여한다.

### 2. Make it adaptable

시스템을 변경 불가능한 진리로 취급하면 실제 문제를 해결하지 못하는 사용자가 우회한다. Governance는 다음을 답해야 한다.

- 기존 패턴이 특정 사례에 부족할 때 수정, 다른 패턴, 새 패턴 중 무엇을 택하는가?
- 새 패턴 요청을 누가 받고 어떤 증거로 승인하는가?
- 버그와 접근성·성능 개선은 어떻게 우선순위를 정하는가?
- 누가 디자인·코드·문서를 바꾸고 승인하는가?
- 변경을 제품에 어떻게 배포하고 사용자에게 어떻게 알리는가?
- 오래되거나 위험한 패턴을 어떤 대체안과 기간으로 폐기하는가?

변화는 수정, 추가, 제거로 나뉜다.

- 수정: 기능, 버그, 시각, 성능, 접근성, 리팩터링, UX 개선을 시스템과 소비 제품에 함께 전달한다.
- 추가: 한 번의 특수 요구를 곧바로 공용 패턴으로 만들지 않는다. 다른 맥락에서도 반복되거나 명확한 재사용성이 있는지 확인한다.
- 제거: 사용처를 먼저 찾고, 대체 패턴과 migration 기간을 알린 뒤 단계적으로 폐기한다.

### 3. Make it maintainable

- 업데이트 마찰이 크면 사람들은 결국 문서와 패턴 갱신을 포기한다.
- 가장 이상적인 구조는 패턴 코드, 문서 예시, production이 같은 소스를 사용해 한 변경이 함께 반영되는 것이다.
- 조직과 기술이 분산돼 완전 동기화가 비현실적일 수 있다. 이때는 작동하는 수준의 공통 패턴, 문서, 버전 관리부터 시작한다.
- 공유 가능한 CSS/JS보다 백엔드 로직과 얽힌 markup 동기화가 어려울 수 있다. 템플릿이나 컴포넌트 패키지가 다리 역할을 할 수 있지만 프로젝트 기술에 맞춰 결정한다.

### 4. Make it cross-disciplinary

- 패턴 문서를 개발 코드 스니펫으로만 만들지 않는다.
- 콘텐츠 길이, 편집 책임, 비즈니스 규칙, UX, 접근성, 성능, 백엔드 계약 등 관련 직군의 고려사항을 한 패턴 가까이에 모은다.
- 패턴 라이브러리는 조직 전체가 같은 말을 쓰는 공동 작업장이어야 한다.

### 5. Make it approachable

- 첫 목표는 유용한 시스템이며 화려한 문서 사이트가 아니다.
- 공식화된 뒤에는 목적, 대상, 사용법이 명확하고 찾기 쉬운 문서 경험에 투자한다.
- 접근하기 좋은 문서는 비개발자의 참여, 인지도, 조직적 신뢰를 높인다.

### 6. Make it visible

- 변경 로그, roadmap, 성공 사례, 사용 팁을 시스템 가까이에 둔다.
- 팀이 실제로 쓰는 채널에서 변경 요청과 release를 알린다.
- pair session, workshop, webinar, tutorial, onboarding으로 사용법을 교육한다.
- issue tracker, office hour, 채팅, forum, 인터뷰, 설문, 정기 review로 지원과 피드백 루프를 만든다.
- 원문은 공개 스타일 가이드의 가시성·책임성·채용 효과를 강조하지만, 실제 공개는 기밀·브랜드·보안·계약을 검토하고 명시적 승인을 받은 경우에만 한다.

### 7. Make it bigger

- UI 패턴이 신뢰받는 허브가 되면 브랜드, 보이스·톤, 글쓰기, 코드, 디자인 원칙을 연결한다.
- 웹·iOS·Android 등 플랫폼 공통 원칙과 의도적인 차이를 함께 문서화할 수 있다.
- 모든 문서를 무조건 한곳에 넣기보다 발견 가능성과 일관성이 실제로 개선되는 범위만 통합한다.

### 8. Make it context-agnostic

- `homepage-carousel`처럼 위치를 이름에 박으면 재사용 범위를 스스로 제한한다.
- `product-card`처럼 현재 콘텐츠를 이름에 박으면 다른 콘텐츠에 쓰기 어렵다.
- 구조와 책임을 중심으로 이름을 짓되, 너무 일반적이라 의미를 잃지 않게 한다.
- 내용이나 페이지 맥락을 가려 보고 구조가 무엇인지 말해보는 naming exercise가 도움이 된다.

### 9. Make it contextual

- 이름은 맥락 독립적으로 짓더라도 문서는 실제 사용 맥락을 풍부하게 제공해야 한다.
- 스크린샷, 동영상, 실제 사용 규칙, 잘못된 사용, 구성 부품, 소비 화면을 보여준다.
- lineage를 통해 변경 시 어떤 패턴과 template/page를 다시 테스트할지 결정한다.

### 10. Make it last

- 지속 가능한 시스템에는 시간, 예산, 돌봄, 변화 절차가 필요하다.
- 관리가 제대로 되면 시스템은 반복되는 학습을 축적해 시간이 갈수록 가치가 커진다.
- 전면 재구축이 있더라도 버튼, 입력, 탭, 콘텐츠 구조, 문서 운영에서 검증된 지식은 보존한다.

## 다섯 장을 관통하는 운영 원칙

1. **화면보다 시스템:** 화면은 시스템의 구체적 인스턴스다.
2. **부분과 전체 왕복:** isolation과 context를 모두 검증한다.
3. **구조와 콘텐츠 공동 설계:** 분리 가능한 구현과 현실적인 데이터 검증을 동시에 한다.
4. **정상 상태만 설계하지 않기:** 상태·권한·밀도·오류·길이의 변형이 시스템의 회복력을 증명한다.
5. **공통 언어:** 분류와 이름은 협업을 돕기 위해 존재하며 교리가 아니다.
6. **실제 환경에서 결정:** 정적 시안은 방향과 대화에 쓰고 동작은 최종 매체에서 확인한다.
7. **다학제 품질:** 접근성, 성능, 콘텐츠, 개발, 비즈니스가 패턴 정의에 함께 들어간다.
8. **살아 있는 단일 진실 공급원:** 예시·문서·구현의 차이를 줄인다.
9. **Governance:** 추가·수정·폐기·배포·교육·지원의 주체와 절차를 둔다.
10. **도구 독립성:** 도구 이름보다 필요한 기능과 팀의 운영 적합성을 선택한다.

## 현대 프로젝트에 적용할 때의 보정

- 현재 접근성 표준, 프레임워크 API, 브라우저 지원, 컨테이너 쿼리, Storybook/Figma 기능 등은 변할 수 있으므로 현재 공식 문서를 확인한다.
- Atomic Design 계층과 코드 컴포넌트 경계를 기계적으로 일치시키지 않는다. 코드 경계는 책임, 상태, 재사용, 성능, 팀 소유권까지 고려한다.
- 모든 작은 화면 수정에 대규모 design-system ceremony를 강요하지 않는다. 영향 범위에 맞게 inventory, 문서, governance 깊이를 조절한다.
- 사용자 문제와 비즈니스 목표가 불분명하면 계층 분류보다 먼저 이를 명확히 한다.
- 기존 시스템이 있으면 새 taxonomy를 덮어쓰지 말고 현재 이름·토큰·컴포넌트·문서에서 출발한다.
- AI가 UI를 생성할 때도 기존 컴포넌트 재사용, 의미 있는 구조, 실제 상태, 접근성, 반응형, 시각 검증, 변경 영향 기록을 동일하게 요구한다.
